# 阶段 2：权威移动

## 实现状态

协议已升级至 v2，包含 `InputCommand` 和按接收者确认输入序号的 `WorldSnapshot`。C++ 服务端以毫米级定点位置在 `30 Hz` Tick 中模拟，默认以 `15 Hz` 广播快照；Godot 客户端发送方向意图并绘制最近快照中的本地与远端实体。

已验证 C++ 三组测试、Godot 无界面加载、双 Godot 客户端的握手/输入/快照流量，以及本机 UDP 右移输入导致权威快照位置变化。提交前仍应在桌面模式下打开两个客户端，目检实体显示和方向输入。

## 目标

完成第一个完整的实时同步闭环：Godot 客户端只发送移动输入，C++ 服务端在固定 Tick 中模拟玩家位置，并向所有已连接客户端广播权威世界快照。两个本地客户端应能看到彼此移动。

本阶段验证“服务端拥有游戏状态”，而不是追求移动手感。以 `30 Hz` 模拟、`30 Hz` 输入、`15 Hz` 快照作为正确性基线；客户端预测、插值、重连、可靠重传和 AOI 都留给后续阶段。

## 实施顺序

1. 扩展 [`shared/protocol/protocol.md`](../shared/protocol/protocol.md)，新增 `InputCommand` 和 `WorldSnapshot` 的消息类型、字段、字节序及长度限制。
2. 在 `shared/protocol/test_vectors/` 添加固定输入包和快照包样本，并在 `server/tests/` 添加对应的编码、解码和畸形包测试。
3. 服务端新增最小 `PlayerState`：`client_id`、二维位置、当前移动轴、最后接受的输入序号。`Hello` 成功后创建状态。
4. 客户端以可配置频率发送移动意图：输入序号、客户端 Tick、`move_x`、`move_y`。第一版使用 `30 Hz`，位置不随本地输入直接改变。
5. 服务端以可配置频率校验并应用最后有效输入；第一版每个 `30 Hz` Tick 模拟一次、每 `2` 个 Tick（`15 Hz`）向所有客户端发送世界快照。频率不应假定总是整除。
6. Godot 根据最近快照绘制简单方块或圆形。先区分自己与其他玩家，不引入角色资源或动画。

## 初版数据约束

- 移动轴使用有符号 8 位整数，取值只能是 `-1`、`0`、`1`。
- 服务端限制最大速度和世界边界；未知玩家、错误长度和非法轴值直接丢弃。
- 快照带 `server_tick` 与已确认的输入序号，为阶段 3 的预测和校正预留基础。
- 快照只包含已连接玩家的 ID 和位置；不做压缩、差量同步或 AOI。
- `InputCommand` 第一版必须带 `client_tick`。未来若需要子 Tick 输入时间，应通过新的协议版本增加命名字段，不能复用未定义的保留字节。

## 高频运行档

阶段 2 只验收 `30/30/15 Hz` 基线。世界状态正确后，在后续性能实验中依次启用 `64 Hz` 和 `128 Hz` 模拟档：它们的单 Tick 预算分别为 `15.625 ms` 和 `7.8125 ms`。每次提高频率都要记录 Tick P50/P95/P99、超时 Tick 数、输入积压、快照频率、每秒包数和字节数。

`128 Hz` 模拟不等于 `128 Hz` 完整快照广播；快照频率与大小必须独立控制，否则带宽和序列化成本会遮蔽真正的模拟性能问题。

## 验收

- 两个 Godot 窗口连接到同一服务端后，可以看到彼此的权威位置变化。
- 修改客户端本地显示位置不会改变服务端下一帧快照中的位置。
- 服务端日志包含连接数、每秒输入包数、快照包数和快照字节数。
- C++ 编解码测试、固定 Tick 测试、Godot 无界面加载均通过。

## 完成边界

阶段 2 结束时，移动在高延迟下可能显得生硬，这是预期结果。阶段 3 将用快照缓冲、插值、本地预测、服务端确认和输入重放解决该体验问题。
