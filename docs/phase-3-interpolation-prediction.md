# 阶段 3：插值、预测与校正

## 当前状态

阶段 3 功能已实现。v2 线协议保持不变；新增逻辑全部位于 Godot 客户端，并通过纯算法测试、无界面工程加载和双客户端劣化网络闭环验证。桌面双窗口的移动手感与红色校正线仍应由开发者最终目检。

## 目标

在阶段 2 的权威移动闭环上改善视觉与操作体验：远端实体使用快照缓冲平滑显示；本地实体立即响应输入，并在收到服务端快照后回到权威状态。服务端仍然是位置的唯一事实来源。

本阶段不改变 v2 的基本权威边界。`WorldSnapshot` 已包含 `server_tick`、当前客户端的 `acknowledged_input_sequence` 和所有实体位置，足以实现第一版插值与校正。

## 范围与非目标

包含：

- 远端实体快照缓冲和线性插值。
- 本地固定步长预测、输入暂存、服务端确认和输入重放。
- 预测误差、校正次数、快照年龄与插值延迟诊断。
- 乱序或重复快照的丢弃规则。

不包含：

- 修改服务端权威位置的客户端逻辑。
- 技能、命中判定、服务端历史回溯或延迟补偿。
- 可靠 UDP、断线重连、AOI、差量快照和压缩。
- 通过视觉平滑掩盖持续的服务端逻辑错误。

## 远端实体插值

实现位于 `client/scripts/snapshot_buffer.gd` 和 `world_view.gd`。每个远端 `client_id` 拥有独立缓冲，最多保存 32 个样本。样本包含 `server_tick`、本机接收时间和毫米位置。客户端与服务端不需要同步系统时钟。

`server_tick` 小于或等于最近 Tick 的整包直接丢弃，实体位置、玩家列表、快照年龄和界面 Tick 因而始终来自同一条最新时间线。该比较暂不处理 uint32 Tick 回绕；30 Hz 下连续运行数年才会触发。

渲染时不显示“刚收到的最新状态”，而是选择一个稍早的目标时间：

```text
render_time = local_now - interpolation_delay
```

第一版默认 `interpolation_delay = 100 ms`。在缓冲中找到包围 `render_time` 的两个快照 `A` 和 `B`，按比例线性插值位置：

```text
position = lerp(A.position, B.position, t)
```

目标时间早于首帧时保持首帧，晚于末帧时保持末帧。当前版本不外推远端实体，避免丢包后沿错误方向继续移动。两个包在同一次轮询中交付、接收时间相同时，直接采用较新的 Tick。

## 本地预测与校正

实现位于 `client/scripts/local_prediction.gd`。`NetworkClient` 只有在数据报被真实 UDP 层或网络模拟队列接受后才发出 `input_command_sent`；随后客户端立即推进预测位置，并把命令保存在 `pending_inputs`：

```text
PendingInput {
  input_sequence
  client_tick
  move_x, move_y
}
```

收到包含本地实体的世界快照后：

1. 读取权威位置和 `acknowledged_input_sequence`。
2. 丢弃序号小于或等于确认序号的待确认输入。
3. 将预测位置重置为服务端权威位置。
4. 按原顺序重放剩余 `pending_inputs`。
5. 比较“校正前预测位置”和“权威位置加重放结果”，记录实际视觉跳变距离。

第一份权威快照只建立共同起点，不计为校正。后续误差大于 0 时增加校正次数，并用 0.35 秒红线显示校正前后位置。红线只属于渲染诊断；模拟状态直接采用重算结果，不用视觉平滑掩盖持续分歧。

待确认队列上限为 256。超限时丢弃最老输入并增加 `dropped` 诊断；这会降低下一次重放精度，但能确保断网时内存有界。

## 共享移动规则

预测只有在客户端与服务端使用完全相同的移动规则时才可靠。阶段 3 开始前应把以下常量和规则写入跨端契约，并在两端以同一固定单位实现：

- 位置单位：毫米整数。
- 模拟频率：阶段 3 基线为 `30 Hz`。
- 速度：`3000 mm/s`，即基线下每 Tick `100 mm`。
- 世界边界：`±9000 mm`。
- 输入轴范围：`-1`、`0`、`1`。

阶段 3 明确延续逐轴移动：X、Y 分别增加 `100 mm` 并裁剪，所以对角速度是单轴的约 1.414 倍。当前选择是为了与阶段 2 权威模拟完全一致；若以后归一化，必须同时修改 C++、GDScript、跨端契约和测试。

## 网络劣化与对照实验

`network_client.gd` 在协议层与 UDP 套接字之间提供默认关闭的双向劣化队列。延迟是单程值，因此 `100 ms` 配置会让 RTT 基线增加约 `200 ms`。固定种子使丢包和抖动序列可复现：

```powershell
& "F:\godot\Godot_v4.7.1-stable_win64_console.exe" --path client -- `
  --latency-ms=100 --jitter-ms=20 --loss-percent=5 --seed=1337
```

使用 `--disable-prediction` 关闭本地预测；使用 `--interpolation-ms=0` 退回最新快照显示。诊断面板显示 RTT、快照年龄、插值延迟、远端数量、待确认输入数、最近误差、校正次数、队列丢弃数和模拟丢包数。

## 测试

纯算法测试覆盖中点插值、首末帧保持、重复/乱序拒绝、输入确认删除、未确认输入重放和误差计数：

```powershell
& "F:\godot\Godot_v4.7.1-stable_win64_console.exe" --headless --path client `
  --script res://tests/phase3_algorithms_test.gd
```

本次双客户端验证使用 `100 ms` 单程延迟、`±20 ms` 抖动、`5%` 丢包和不同固定种子。服务端稳定记录 2 个玩家，每秒接收约 51–60 个输入，并发送 30 个双实体快照；客户端无脚本错误，服务端只按既有规则拒绝少量乱序输入。

## 完成边界

当前确认语义是“服务端最近接受的输入序号”，服务端每 Tick 应用最近输入，而不是逐条消费所有命令。因此高抖动下客户端的一命令一步重放是近似模型，权威快照会持续收敛误差。阶段 4 若加入子 Tick 战斗输入，应先明确输入应用 Tick，再扩展协议。

阶段 3 不处理战斗命中、服务端回溯、断线移除或大规模实体。阶段 4 再加入带历史状态的技能与延迟补偿实验。
