# 同步模型

## 当前闭环

客户端只采集输入意图，服务端是玩家位置和游戏结果的唯一权威来源。阶段 1 已完成 UDP 握手与 RTT 测量；阶段 2 将建立最小移动闭环：

```text
Godot 输入
  -> InputCommand(sequence, client_tick, move_x, move_y)
  -> C++ 接收与校验
  -> 固定 Tick 世界模拟
  -> WorldSnapshot(server_tick, acknowledged_input, entities)
  -> Godot 显示最近权威状态
```

客户端不能把本地位置作为事实发送。服务端只接受合法输入，并在自己的时间轴上计算位置。

## 三种频率

| 控制项 | 阶段 2 基线 | 职责 |
| --- | ---: | --- |
| 模拟 Tick | 30 Hz | 服务端推进权威世界。 |
| 输入发送 | 30 Hz | 客户端发送当前输入意图。 |
| 快照发送 | 15 Hz | 服务端广播可显示的世界状态。 |

三者必须可独立配置。较高模拟频率不自动要求同频率完整快照广播。

## 后续演进

阶段 3 在快照模型之上增加远端插值、本地预测、服务端确认和未确认输入重放。高频运行档下，`client_tick` 仍是输入排序基础；需要更细粒度输入时，通过新的协议版本增加明确的子 Tick 时间字段，不能复用未定义填充字节。

## 并行开发边界

客户端任务可以实现输入采集、网络收发、实体显示和诊断 UI；服务端任务可以实现输入校验、世界模拟和快照生成。任何一方都不能单独修改 `shared/protocol/` 的既有字段语义。跨端消息变更应作为一项包含双方实现和测试向量的完整任务提交。
